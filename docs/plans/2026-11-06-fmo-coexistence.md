# FMO与RF Link双入口兼容扩展

## 修正背景

原教程要求将广播新身份应用到原SAS，可能破坏FMO客户端绑定的原服务器身份。业务必须区分“新建RF Link服务器”和“已有FMO增加RF Link入口”；Compose/原生只是运行方式，不能代替场景选择。

## 选定结构

```text
同一MQTT Broker
  原FMO端口（示例1883） → 原FMO SAS → 原服务器UID/指纹
  新RF Link端口（示例1884） → 新RF Link SAS → 广播申请的新UID/指纹
                                      ↑
                          Beacon广播新端口对应的身份和端点
```

端口均为示例，应可配置且避免冲突。新SAS须有独立配置、持久卷/目录、HTTP监听和容器名/服务名。复用Broker不等于共享认证链；新认证器仅绑定新监听器，原FMO端口/认证/数据保持。

新端口必须出现在新SAS的MQTT端点和Beacon本地station中；宿主机映射、容器内监听与防火墙须逐层说明。不要额外创建另一个Broker冒充同Broker新增入口，也不要使用任一SAS成功就放行的全局认证回退。

## 实施步骤

1. 增加业务场景选择；原部署识别仅用于确定新RF Link SAS的安装形式，不能生成覆盖原FMO SAS的应用步骤。
2. 提供独立RF Link SAS Compose及原生启动配置，默认不读取或复用原FMO SAS的数据目录。
3. 针对已核验的EMQX版本提供新监听器及专用HTTP认证模板。现有配置仅增量合并，不覆盖默认监听器或全局认证；不支持的Broker版本明确失败。
4. 教程分成新建与兼容扩展两条主线。兼容扩展选择一个新端口，申请身份，生成新SAS配置，接上新监听器，验证后广播。
5. 用临时身份和隔离Broker验证原端口正向接入、RF Link新端口正向接入、错误/匿名/后端不可用拒绝、认证隔离、双端口消息/ACL与撤回新增服务后的FMO不受影响。
6. 完成后再提交/推送、CI和实际合法客户端验收；不修改现有生产服务器或发送真实APRS，除非另有授权。
